# Certificate outage, 24 to 29 September 2026

For 118 hours, from 24 September 2026 03:12 UTC to 29 September 2026 01:32 UTC, every
HTTPS address under `www.ben-cobb.com` showed a certificate error. That included this
app at `https://www.ben-cobb.com/mmu-json-parser/`. The certificate had expired because
GitHub Pages had not renewed it. The only fault found was in the domain's DNS records
at Namecheap. Once those were corrected and the custom domain was saved again, GitHub
issued a new certificate.

The app and its deployment were not at fault and were not changed.

This page records what happened and every change that was made. The steps to follow if
it happens again are in the [README](../../README.md#when-the-certificate-breaks).

## How the pieces fit

- This app is published by GitHub Pages from the `gh-pages` branch of this repository.
- It appears under `www.ben-cobb.com` only because the account's user site,
  `ben-cobb/ben-cobb.github.io`, has that custom domain. GitHub serves every project
  site of an account under the user site's domain.
- The domain is registered at Namecheap, which also hosts its DNS and forwards its
  e-mail.
- GitHub obtains the certificate from Let's Encrypt and is meant to renew it without
  anyone's help, about 30 days before it expires.

Three of the four things that can break the certificate therefore live outside this
repository: the DNS records, the user site's Pages settings, and GitHub's renewal.

| Period (UTC) | What visitors saw |

## Cause

### What the DNS looked like

Before the repair Namecheap's name servers answered like this:

| Name | Type | Answer | Origin |
| --- | --- | --- | --- |
| `www` | CNAME | `ben-cobb.github.io.` | Host record. Correct |
| `www` | A | `185.199.108.153` to `185.199.111.153` | Four A records entered on `www`. They belong on `@` |
| `www` | A | `162.255.119.104` | Generated by a URL Redirect Record on `www` |
| `@` | A | `162.255.119.104` | Generated by a URL Redirect Record on `@` |

`162.255.119.104` is the server behind Namecheap's URL redirects. Both redirects
pointed at `https://www.ben-cobb.com/`, so the one on `www` sent the name to itself.

### Why that breaks renewal

A name that has a CNAME must have no other records. When it does, the answer depends
on who is asked and for what. Asked for the IPv4 address of `www`, Namecheap's name
servers and the public resolvers of Cloudflare and Google returned the five A records.
Asked for the IPv6 address, the name servers returned the CNAME instead. GitHub's own
check, run on 28 September at 20:12, saw only the CNAME.

GitHub does not issue a certificate for a name that leads to an address other than
its own. Its published health check answers "not eligible" as soon as one A or AAAA
record is not a GitHub Pages address, and its documentation names extra records as a
reason certificates fail to generate. Whether a renewal attempt passed therefore
depended on which answer GitHub's resolver held at that moment. That fits the record:
renewals arrived on schedule for six years, turned late in 2026, and then stopped.

### What is established and what is not

Established:

- The certificate expired and GitHub's renewal request was stuck.
- The DNS records conflicted, and resolvers gave different answers at the same time.
- With the records corrected, a certificate covering both names was issued within a
  minute of the settings page being opened.

Not established:

- That the conflict is what stalled the renewal. GitHub does not say why a request
  stalls. Other users reported Pages certificates stuck for days in the summer of 2026
  with correct DNS. Here, too, the request did not move after the domain was attached
  again, until someone opened the settings page.

The conflict is the most likely cause and the only fault found. The first renewal
without anyone's help, due about 28 November 2026, is the real test.

## What was changed

### DNS records at Namecheap

| Record | Before | After |
| --- | --- | --- |
| CNAME `www` to `ben-cobb.github.io.` | present | unchanged |
| A `www` to GitHub's four addresses | present | removed |
| URL Redirect `www` to `https://www.ben-cobb.com/` (301) | present | deleted |
| URL Redirect `@` to `https://www.ben-cobb.com/` (301) | present | deleted |
| A `@` to GitHub's four addresses | absent | added |
| TXT `_github-pages-challenge-ben-cobb` | absent | added |
| MX and SPF on `@` (e-mail forwarding) | present | unchanged |

The name servers now answer `www` with the CNAME alone, and `@` with GitHub's four
addresses: `185.199.108.153`, `185.199.109.153`, `185.199.110.153` and
`185.199.111.153`.

| User site, certificate | `www` only, expired 24 Sep 2026 | `www` and `ben-cobb.com`, valid 29 Sep to 28 Dec 2026 |

| --- | --- | --- | --- |
| Old | `0544BC36FFEF52FC11DAE57E68A5C4AC10B2` | 2026-06-26 03:12:22 to 2026-09-24 03:12:21 | `www.ben-cobb.com` |
| New | `05D596F239FCD41FE3E82E17CC2245345C23` | 2026-09-29 00:33:02 to 2026-12-28 00:33:01 | `ben-cobb.com`, `www.ben-cobb.com` |

Let's Encrypt issued both, through its intermediate YR2.

The settings were changed with these commands. The Pages settings page of the user
site does the same through its Remove, Save and Enforce HTTPS controls.

```sh
# detach, then attach again
echo '{"cname":null}' | gh api -X PUT repos/ben-cobb/ben-cobb.github.io/pages --input -
gh api -X PUT repos/ben-cobb/ben-cobb.github.io/pages -f cname=www.ben-cobb.com

# once the certificate is approved
gh api -X PUT repos/ben-cobb/ben-cobb.github.io/pages -F https_enforced=true
gh api -X PUT repos/ben-cobb/mmu-json-parser/pages -F https_enforced=true
```

### This repository

Pull request [#1](https://github.com/ben-cobb/mmu-json-parser/pull/1), merged as
`85318fde`, added two files and extended the README. No application code changed.

| File | Purpose |
| --- | --- |
| `scripts/check-site-health.sh` | Checks the page, the certificate, the custom domain and the DNS records. Exit status 0 when healthy, 1 when not |
| `.github/workflows/site-health.yml` | Runs the script daily at 14:23 UTC, on demand, and on pull requests that change the check |
| `README.md` | Where the app runs, how the check works, and the steps to take when the certificate breaks |

The first draft of the check was written without access to the domain. Two defects
were fixed before it was merged. Either one would have kept the alarm silent through
this outage.

- The workflow sent the script's output through a pipe, and the step took its status
  from the last command in the pipe. The step was green even when the check failed.
- The DNS section printed the records and judged nothing. It listed
  `162.255.119.104` among the addresses of `www` without flagging it.

### Not changed

- The app's code and its deployment. The `gh-pages` branch still holds the build of
  15 July 2026.
- The contents of the user site repository.
- Mail settings at Namecheap.

## What to watch for

| When | What |
| --- | --- |
| about 28 Nov 2026 | GitHub should renew the certificate by itself. `gh api repos/ben-cobb/ben-cobb.github.io/pages --jq .https_certificate` should then show an expiry near the end of February 2027 |
| **about 28 Nov 2026** | **GitHub pauses the daily check** unless the repository has seen activity in the 60 days before. It sends a warning e-mail first. Re-enable the workflow from the Actions tab, or push any commit |
| from 14 Dec 2026 | The daily check fails if the certificate has not been renewed. Follow the README. If DNS is clean, open the Pages settings page and contact GitHub Support |
| 26 Jan 2027 | The domain registration expires. Make sure auto-renew is on at Namecheap |
| 10 Feb 2027 and 16 Feb 2028 | Let's Encrypt shortens certificate lifetimes to 64 and then to 45 days. If the check starts failing although renewals arrive, lower `MIN_DAYS` in the workflow |

The second row matters most. The pause falls on the date of the first renewal and two
weeks before the check would report a missed one. A paused check reports nothing.

## Lessons

- **Namecheap shows only the first five host records.** The rest are behind "Show
  more". The two redirect records sat there unseen through the first round of edits.
- **A URL Redirect Record brings a hidden address record with it.** Namecheap never
  lists `162.255.119.104`. It exists for as long as the redirect does.
- **Remove the redirect before the address records, not after.** For four hours `www`
  led only to Namecheap, because GitHub's addresses had been taken off it while the
  redirect was still in place.
- **Attaching the domain through the API did not start the certificate request.**
  Opening the Pages settings page did, within a minute.
- **Test that an alarm can go off.** The first draft of the workflow could only ever
  be green.
- **In a clone with an `upstream` remote, `gh` acts on the upstream repository.** Here
  that is someone else's. Pass `-R ben-cobb/mmu-json-parser`.

## Found along the way, not part of this outage

- The deployed page asks for `manifest.json` and gets a 404. The `gh-pages` branch
  carries a `.gitignore` that ends in `*.json`, so the deploy step leaves out every
  JSON file of the build. Harmless.
- `MAINTENANCE.md`, `CLAUDE.md` and `AGENTS.md` in the user site repository say the
  custom domain "is preserved by the root `CNAME` file". With GitHub Actions as the
  Pages source GitHub ignores that file. The domain lives in the repository's Pages
  settings.
